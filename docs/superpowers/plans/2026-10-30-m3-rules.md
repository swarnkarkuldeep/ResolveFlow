# M3 Automation Rules Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (chosen by user). Steps use checkbox (`- [ ]`) syntax. Frontend tasks (T6–T8) follow `frontend-design:frontend-design` and the M1 Design Language.

**Goal:** Admins can define assignment/priority/tagging/status/notify/escalate rules over a small fixed vocabulary, test them on a synthetic ticket, activate them only after a passing test of that exact version, and see on every ticket which rules ran and why. Basic teams (with round-robin) make assignment useful.

**Architecture:** A pure rules core (`rules/engine.py`: condition evaluation + conflict-resolved action plan, no I/O) is wrapped by an executor that, inside the same transaction as the triggering change, loads active rule versions, evaluates, applies the plan through the existing ticket services as actor `rule`, and records one `rule_executions` row per rule per event. Dry runs use the same pure core and write nothing. Rules are versioned and immutable; a test record is bound to a rule version's content hash.

**Tech Stack:** M1/M2 stack. No new dependencies.

**Spec:** design §7.4, §7.2 (teams), §12 M3; PRD FR-16..FR-21, FR-8.

## Global Constraints

- Triggers: `ticket.created`, `message.received` (customer message), `status.changed`, `sla.threshold` (level `warning|breach`). Conditions: AND/OR groups over fixed fields only (sender email, sender domain, subject, body, channel, priority, status, tags, assignee state); operators `equals|not_equals|contains|not_contains|contains_any|starts_with|ends_with|in|is_empty|is_not_empty`; **no regex, no custom fields** (decided).
- Actions: `assign` (user | team | round-robin over a team), `set_priority`, `add_tag`, `set_status`, `notify` (user | team | assignee | owners_admins), `escalate` (assign to a user/team **and** notify owners/admins). **No automated customer replies** (decided).
- **A passing test is bound to the exact rule version** (content hash). Any modification creates a new version with no passing test; activation (and rollback to an older version) requires a passing positive test of that exact version (user clarification).
- Conflict policy (design): rules run in explicit order; per action type the first match wins for `assign`, `set_priority`, `set_status`; `add_tag` is additive; `notify`/`escalate` all fire but are deduped by (type, target).
- Loop guard: rule-caused changes may trigger further rules to a depth of 3; a rule fires at most once per ticket per chain.
- Rules act as audit actor type `rule` (actor_id = rule id); every execution is recorded.
- Permissions: new `rule:read` (Owner, Admin), `rule:manage` (Owner, Admin), `team:manage` (Owner, Admin); everyone with `ticket:read` can see the "why" panel on a ticket. Teams are flat groups (no hierarchy). Deferred features never appear in the UI; no mock data.
- Notification *intents* are written to a `notifications` table by `notify`/`escalate`; delivering and displaying them is M4 (no notification UI in M3).
- Branch `m3-rules`; Conventional Commits; push per task; PR + merge + tag `m3-complete` after full verification.

## Review Focus

- A rule edited after it was tested: the new version cannot be activated until it has its own passing test; the previously active version keeps running meanwhile; rollback to an old tested version works.
- Rules that trigger each other (assign→status→assign…): the chain stops at depth 3, once per rule per ticket, with no deadlock or unbounded growth.
- Round-robin with deactivated members, viewers, an empty team, and two concurrent tickets (no duplicate pick of the same person, no lost update).
- Two rules setting the same thing: first by order wins, the loser is recorded as "skipped: overridden by rule X" and shown in the why panel.
- Another workspace's rule/team/user ids (in definitions or URLs) never apply or leak (404/422), including assignees and team targets inside a rule definition.
- A rule that fails (e.g. its target user was deactivated) must not break the ticket change that triggered it; the failure is recorded.

### Task 1: Pure rules engine

**Files:** Create `rules/engine.py`, `rules/schema.py`, `tests/test_rules_engine.py`.

**Interfaces — Produces:**
- `schema.RuleDefinition` (Pydantic): `trigger: {event: Literal[4], level: Literal["warning","breach"] | None}`, `conditions: Group`, `actions: list[Action]` (1..10). `Group = {op: "and"|"or", items: list[Condition | Group]}` (depth ≤ 3, ≤ 20 conditions). `Condition = {field, operator, value}` with a field→operators table validated (`FIELD_OPERATORS`). Action union by `type`. `schema.canonical_hash(defn) -> str` (sha256 of canonical JSON).
- `engine.TicketFacts(event, level, sender_email, sender_domain, subject, body, channel, priority, status, tags: frozenset[str], assignee_id: str | None)`.
- `engine.evaluate_group(group, facts) -> GroupResult` (a tree of `{passed, op, children | {field, operator, value, actual, passed}}`).
- `engine.plan(rules: Sequence[RuleInput(id, name, position, definition)], facts) -> Plan(results: list[RuleResult(rule_id, name, matched, trace)], actions: list[PlannedAction(rule_id, rule_name, type, params, status: "apply"|"skipped", reason: str | None)])` applying the conflict policy above. Text comparisons are case-insensitive; `contains_any` takes a list; empty groups pass (`and`) / fail (`or`).
